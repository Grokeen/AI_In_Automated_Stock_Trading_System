이 문서는 **어떻게 개발하고 검증·인계할지**를 정한다. 요청서는 범위와 완료 기준, 정의서는 현재 구현과 목표 구조, 분장표는 역할별 책임을 정한다. 절차 정의가 매매 기능의 구현·검증 완료를 뜻하지 않는다. 불일치가 발견되면 최신 사용자 요청과 실제 근거에 맞춰 정리하고 변경 이유를 남긴다.

## 1. 기본 원칙

1. **작게 끝낸다.** 한 작업은 확인 가능한 동작이나 산출물을 중심으로 잡는다. 설정 검증, 응답 소실 후 대사, 상태 표시 명세 등을 각각 검증·인계할 수 있게 나눈다.
2. **계약부터 맞춘다.** 입력·출력·오류·상태·저장 형식을 정하고 관련 역할에 공유한 뒤 구현한다. 전체 상세 설계가 끝날 때까지 모든 개발을 기다리지는 않는다.
3. **중요한 실패부터 다룬다.** 주문 중복·응답 소실·저장 실패·모드 혼동·한도 초과를 성공 경로와 함께 설계한다.
4. **외부 계정 없이도 진척시킨다.** 가짜 증권사와 고정 데이터로 개발하고 실제 모의 API 연결은 별도로 검증한다.
5. **NAS 기능을 함께 확인한다.** 매매 프로그램 실행과 기존 파일 공유·서비스 정상을 각각 확인한다.
6. **근거를 구분한다.** 사실·가정·미정, 과거·현재 측정, 가짜 응답·실제 모의 서버 결과를 구별한다.

초기 구조는 가벼운 Python 모듈형 애플리케이션을 기준으로 한다. 큰 프레임워크·다수 컨테이너·별도 서비스 분리는 필요성과 운영 비용이 확인될 때 도입한다. 기존 `nas/` 운영 도구와 새 매매 기능의 경계는 유지한다.

## 2. 단계별 개발 순서

[요청서](PROJECT_REQUEST.md)의 S0~S5를 사용한다. 새로운 단계 번호로 진척을 중복 계산하지 않는다.

| 단계 | 개발 방법 | 산출물·종료 기준 | 주담당 |
|---|---|---|---|
| S0 환경 확인 | 실제 Python·armhf·TLS·저장 경로·서비스와 공식 API 조건 확인 | 환경 기록, 제약·미정 목록 | OPS, RES 지원 |
| S1 오프라인 개발 | 설정·모델·가짜 증권사·주문 기록·위험 한도부터 작은 동작으로 구현 | 키 없이 정상·오류·중복·재시작 검증 | DEV, DES·AUD 지원 |
| S2 모의 계좌 조회 | 모의 인증·시세·잔고 조회부터 연결 | 서버·계좌 일치, 속도 제한·비밀정보 제외 확인 | DEV, RES·AUD 지원 |
| S3 모의 매매 | 신호→위험 검사→주문→체결·취소→기록·복구 연결 | 지원 동작 검증, 미지원·미검증 범위 기록 | DEV, AUD 검토 |
| S4 NAS 배포 | 검증한 버전을 설치하고 자원·저장·동시 공유·복구 확인 | 설치본 식별, 공존·복구 근거, 운영·인계 문서 | OPS, DEV·AUD·DOC 지원 |
| S5 AI 확장 | PC 등 별도 환경에서 데이터·모델·비용·표본 외 성능 연구 | 재현 가능한 실험, NAS 전달·자원 조건 | RES, DEV·OPS·AUD 지원 |

계좌·키가 없으면 S2·S3 실통신 검사만 선행 입력 대기로 표시한다. S1·설계·조사·문서는 계속 진행한다. API 통신 모드는 paper를 기본으로 하고 offline은 명시적으로 선택한다. live 실행은 초기 개발·검증 범위에 포함하지 않는다.

## 3. 한 작업을 수행하는 절차

| 순서 | 수행 내용 | 남길 근거 |
|---|---|---|
| 1. 요구 연결 | 관련 REQ·T·역할별 업무 ID와 이번 범위 정의 | 목표 동작·산출물과 완료 기준 |
| 2. 계약·흐름 정의 | 입력·출력·오류·상태·의존성과 운영자 행동 설계 | 짧은 명세, 예시 데이터, 조율 결과 |
| 3. 검증 계획 | 성공·대표 실패·회귀 영향 선정 | 기대 결과, 외부 계정 필요 여부 |
| 4. 구현 | 프로젝트 소스 경로에서 해당 동작 구현 | 변경 파일·의도, 날짜·역할 주석 |
| 5. 자체 검증 | 필요한 테스트·컴파일·실행 또는 문서 검사 | 명령·환경·실제 결과·미검증 항목 |
| 6. 독립 검토·수정 | AUD의 근거 대조, 관련 역할 확인, 문제 수정 | 재현 가능한 지적과 재검증 결과 |
| 7. 통합·배포·인계 | OPS 통합·배포, DOC 안내·기록 정리 | 커밋·배포 여부·남은 문제·다음 조치 |

작은 변경마다 위 절차를 반복한다. 역할 간 일상적인 조율을 매번 사용자에게 승인받는 절차로 만들지 않는다. 선행 입력이 필요한 부분과 독립적으로 진행할 부분을 나눈다.

### 착수 기록

```text
업무 ID / 역할 / 담당자:
관련 REQ·T 작업:
목표 동작·산출물 / 이번 범위:
기준 커밋 / 담당 파일:
입력·출력·의존성 / 미정 사항:
검증 방법 / 완료 기준:
```

작업 상태와 최종 인계는 [분장표](WORK_ALLOCATION.md)의 인계 양식을 사용한다.

## 4. 설계·구현 규칙

### 4.1 모듈과 데이터 계약

- 시세·계좌 수집, 전략 판단, 위험 검사, 주문·대사, 영속 저장, 운영 상태를 나눈다. [정의서](PROJECT_DEFINITION.md)의 모듈·주문 계약을 구체화한다.
- 전략은 신호를 만들고 주문 관리자가 주문을 전송한다. AI 신호도 동일한 위험 검사를 거친다.
- 내부 주문 ID와 증권사 주문번호, 주문 의도와 체결 결과를 구분한다. 응답은 어댑터에서 공통 모델로 변환한다.
- 가격·금액·통화·수량 단위를 명확히 하고 식별값의 선행 0을 보존한다. 시각은 시간대가 있는 형식을 쓰며 거래 일정·운영자 표시는 Asia/Seoul 기준을 명시한다.
- 조회 실패, 확인된 거절, 결과 불명 주문의 오류 의미를 구분한다. 결과 불명 주문은 조회·대사 없이 무조건 재전송하지 않는다.

### 4.2 환경과 의존성

- 실제 NAS Python·armhf 환경을 확인하고 최소·검증 버전을 정한다. 커널 aarch64만 보고 arm64 패키지나 Python 3.11 이상을 전제하지 않는다.
- 필요한 라이브러리만 선택하고 환경에 맞는 의존성 고정 파일과 설치 절차를 남긴다. 운영 OS의 공용 Python 패키지를 무분별하게 변경하지 않는다.
- 가상환경을 쓰면 서비스 실행 경로, `DynamicUser` 권한과 상태 경로 접근을 검증한다.
- 인증정보는 보호된 운영 설정에서 주입하고 테스트·로그·문서에 실값을 넣지 않는다.
- `/opt/nas-trader/main.py` 진입점과 `/var/lib/nas-trader` 상태·DB 계약을 맞춘다. 기존 NAS 배포 도구에는 매매 코드 설치 기능이 없으므로 해당 배포 범위를 구현한다.

### 4.3 기능을 나누는 예

“주문 엔진 전체”를 한 번에 완료로 처리하지 않고 다음처럼 나눈다.

1. 주문 의도를 저장하고 다시 읽기.
2. 가짜 증권사로 접수·거절·부분체결 처리.
3. 응답 소실 시 결과 불명 기록과 조회·대사.
4. 재시작 후 복구와 중복 전송 방지.
5. 모의 서버가 지원하는 동작을 실제 모의 계좌에서 확인.

각 변경에 관련 테스트·근거를 붙인다. 미지원 동작을 실제 모의 서버에서 검증한 것으로 표시하지 않는다.

## 5. 여섯 역할의 참여 방식

| 역할 | 개발 과정에서 하는 일 | 다음 인계 |
|---|---|---|
| OPS 배포관리 | 환경·실행 계약 제공, 통합·NAS 공존·복구 검증 | DEV에 환경, AUD·DOC에 운영 결과 |
| DES 디자인 | 흐름·용어·상태·오류·조작 명세, 구현에서 의미 확인 | DEV에 명세, AUD에 시나리오 |
| DEV 개발자 | 계약 구체화, 작은 기능 구현·자체 검증·수정 | AUD에 근거, OPS에 실행 가능한 버전 |
| AUD 감사 | 요구 검증표 작성, 코드·테스트·배포 근거 독립 확인 | 소유자에 지적, OPS·DOC에 품질 상태 |
| RES 연구 | 공식 API·시장·데이터·전략·비용과 실험 근거 제공 | DEV에 조건, OPS에 운영 제약 |
| DOC 문서 | 요청·제안·현재 구현 구분, 실제 결과와 문서 연결 | 다음 작업자·운영자에 재현 가능한 안내 |

독립 파일 영역과 설계·조사·검증 계획은 함께 진행할 수 있다. 공통 모델·DB 스키마·설정 계약·같은 파일을 바꾸는 작업은 담당자와 의존성을 맞춘다. AUD의 품질 평가와 RES의 타당성 평가는 각각 근거를 남긴다.

## 6. 테스트와 검증 방법

| 변경 | 필요한 검사 | 판단 기준 |
|---|---|---|
| 설정·위험 한도·주문·저장 | 핵심 단위 테스트와 실패·복구 통합 테스트 | 동작·상태 변화·데이터 보존 확인 |
| 증권사 어댑터 | 공식 형식의 비밀정보 없는 응답 예제, 가짜 HTTP, 모의 API | 호출 한도·환경·오류 의미·지원 범위 확인 |
| 시세·스케줄 | 고정 시각·데이터로 지연·역순·휴장·재연결 재현 | 오래된 정보로 새 주문을 만들지 않음 |
| 운영 흐름·상태 | 정상·실패·중지의 표시·조작 시나리오 | 모드·중지·취소·청산의 의미가 명확함 |
| systemd·배포·의존성 | 설정·컴파일, NAS 실기·권한·자원·공유·복구 | 대상 장비에서 재현, 기존 NAS 유지 |
| 문서만 변경 | 링크·구문·인코딩·버전·용어·상태·Git 범위 | 근거와 일관성, 의도하지 않은 코드 변경 없음 |

주문·위험 한도·복구는 기대 동작과 회귀 테스트를 먼저 구체화한다. 모든 단순 수정에 테스트 파일을 추가하거나 구현을 그대로 반복하는 테스트를 만들 필요는 없다. 적절한 검사가 통과하면 새로운 변경·실패·미해결 우려가 없는 한 같은 검사를 무의미하게 반복하지 않는다.

### 결과 기록과 자동화

- 명령·커밋·OS·Python·모드·시각·데이터 출처와 실제 결과를 기록한다.
- 통과·실패·미지원·미검증·환경상 제외를 구분한다. offline, 실제 모의 서버, NAS 실기 통과는 별개의 결과다.
- Windows에서 제외된 Linux 테스트를 통과로 계산하지 않는다. 과거 NAS 테스트 9개는 기존 운영 도구의 기록이며 매매 기능의 검증 결과가 아니다.
- 계정이 필요한 검사는 준비 후 수행하고 테스트를 위해 실계좌 주문을 보내지 않는다.
- 검사 명령이 정리되면 비밀정보 없이 실행 가능한 단위·가짜 응답 통합 검사와 Python 컴파일을 GitHub 변경 검토에 연결한다. 문서 변경은 문서 검사를 우선한다. 현재 CI가 이미 구성됐다는 뜻은 아니다.

기존 명령은 [정의서](PROJECT_DEFINITION.md)의 검증 항목을 사용하고, 신규 매매 코드의 검사 명령은 구현과 함께 추가한다.

## 7. Git과 공동 작업

1. 원격 최신 상태와 본인 작업 폴더를 비교하고 기준 커밋·담당 파일을 기록한다.
2. 정상적인 별도 checkout이 가능하면 역할·작업별 브랜치를 사용한다. 이름 예시는 `work/dev/dev-01-config`이며 이미 생성된 브랜치가 아니다.
3. 한 커밋에 설명 가능한 변경을 담고 관련 REQ·업무 ID·검증 근거를 변경 설명에 남긴다.
4. 검증한 파일만 명시적으로 추가하고 차이·공백·변경 목록을 확인한다. 인증정보·로그 원문·백업을 넣지 않는다.
5. 원격과 충돌하면 최신 변경을 확인해 통합하고 강제 푸시로 덮어쓰지 않는다.
6. OPS가 main 통합·릴리스를 조율한다. 각 역할의 자체 검증·기록 책임은 유지된다.

현재 공유 폴더의 `.git`은 미완성 상태로 기록되어 있다. 기존 잠금을 임의 삭제하지 않는다. 별도 Git 메타데이터와 빈 index 주의는 [정의서](PROJECT_DEFINITION.md)의 Git 상태 주의를 따른다.

Z: 개발 폴더와 NAS 공유 소스는 같은 파일이다. 공유 소스 수정, GitHub 반영, `/opt`·`/etc` 운영 파일 설치를 각각 구분한다. 같은 공유 파일을 동시에 덮어쓰지 않는다.

## 8. NAS 배포와 복구

- 배포 전 커밋·설치 파일·환경·offline/paper 모드·미검증 항목을 식별한다. 이전 버전·설정을 보관하고 DB 변경에는 백업·호환·복원 절차를 준비한다.
- 현재 저장공간·서비스·권한·중복 프로세스·API 환경을 확인한다. 문서만 바뀌었다면 NAS 서비스를 재설치하거나 재시작하지 않는다.
- 설치 후 소스 일치, 인터프리터·사용자·상태 경로와 CPU·태스크·주소공간 제한의 실효값을 확인한다. `LimitAS`를 전체 실제 메모리 제한으로 설명하지 않는다.
- 데이터 영속성을 확인하고 재시작 시 조회·대사가 끝난 뒤 새 모의 주문을 허용한다. 매매용 데이터 볼륨과 일반 공유 볼륨을 구분해 검사한다.
- 매매 부하와 파일 공유를 함께 확인한다. 장애 시 새 주문을 멈추고 복구한다. DB 호환성을 확인하지 않은 코드 버전만 되돌리기를 하지 않는다.
- OPS가 배포·복구, DEV가 구현 수정, AUD가 근거 확인, DOC가 안내 갱신을 담당한다. 이 절차는 실제 자금 투입·실거래 활성화를 포함하지 않는다.

## 9. 연구·시장분석·AI 방법

- 공식 출처·확인 날짜·계좌별 추가 확인 사항을 남기고 사실·추정·제안·실험 결과를 나눈다.
- 실험에 데이터 출처·사용 조건·수집 시각·학습/검증 구간·전처리·전략/모델 버전을 기록한다.
- 거래비용·슬리피지·데이터 누출·과적합·표본 외 성능을 다룬다. 모의 체결을 실제 체결 보장으로 해석하지 않는다.
- 큰 학습·백테스트는 별도 PC 등에서 수행하고 NAS에는 가벼운 실행·신호 처리를 우선한다.
- 결과가 구현 조건을 바꾸면 DEV·OPS·DES에 영향을 전달하고 DOC가 근거를 연결한다. AUD는 요구 충족·품질 평가를 별도로 유지한다.

## 10. 완료 기준과 다음 시작점

### 작업 완료 기준

- 관련 요구·업무 ID와 범위가 명확하고 약속한 산출물이 있다.
- 변경에 맞는 검사가 통과했으며 실패·미검증·대기 항목을 숨기지 않았다.
- 필요한 독립 검토 지적을 처리하거나 영향과 후속 조치를 명시했다.
- `UPDATE.md`에 KST 날짜·시간·변경 파일·내용·실제 검증·반영 결과를 적고 `OWERORDER.md`에 보고했다.
- 검증한 파일의 Git 반영과 인계가 확인된다. NAS 배포 대상이면 실제 설치·공존·복구 결과를 별도로 남긴다.

코드 작성, 검토, GitHub 반영, NAS 배포 검증 완료를 같은 상태로 표시하지 않는다. 전체 프로젝트의 완료는 [요청서](PROJECT_REQUEST.md)의 완료 기준으로 판단하며 계획·문서 작성만으로 선언하지 않는다.

### 다음 작업자의 시작점

현재는 매매 기능 구현 전 단계다. [분장표](WORK_ALLOCATION.md)의 역할별 첫 지시를 따른다. OPS·RES는 환경과 공식 조건, DES는 흐름·상태 명세, AUD는 요구 검증표, DOC는 문서 일관성을 정리한다. DEV는 DEV-01의 공통 모델·설정·가짜 증권사부터 시작하고 위 절차로 작은 변경을 반복한다.
