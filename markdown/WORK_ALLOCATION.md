| AUD | 감사 / 요청사항 평가 / 프로젝트 평가 | 요구사항 충족, 구현 정확성, 검증 근거, 운영 품질을 독립적으로 평가 | 요구사항 검증표, 결함·위험 목록, 품질 평가서 |
| RES | 연구 / 시장분석 / 프로젝트 평가 | 증권사·시장·데이터·전략·AI·비용의 타당성과 프로젝트 효용 평가 | 공식 근거 조사, 전략·데이터 연구, 타당성·우선순위 평가서 |

**AUD는 “요청한 기능이 근거를 갖춰 올바르게 구현됐는가”, RES는 “이 접근이 시장·데이터·비용·자원 측면에서 타당한가”를 평가한다.** 두 역할의 평가 결과를 하나의 수익률이나 진척률로 합쳐 표시하지 않는다.

현재 구현은 NAS 운영 도구까지다. 아래 업무는 이후 개발·검토를 위한 배분이며, 기존 검증 기록을 새로 수행한 업무로 계산하지 않는다. KIS는 우선 연동 후보이고 계좌·API 키 준비 여부는 미확인이다.

## 2. 배포관리 — OPS

| 업무 ID | 할 일 | 인계·완료 기준 | 착수 조건 |
|---|---|---|---|
| OPS-01 | NAS의 Python·armhf 호환성·저장공간·기존 서비스·자원 한도·현재 소스를 재확인 | DEV에 실행 환경과 경로 전달, RES의 API 조건 확인 결과를 함께 정리 | 지금 가능, NAS 접속이 가능한 범위에서 진행 |
| OPS-02 | 버전이 식별되는 offline/paper 배포, 상태 확인, DB·설정 백업과 되돌리기 절차 준비 | 검증한 소스와 설치본 일치, 실패 시 이전 상태 복구, NAS 파일 공유 유지 | 초안은 지금 가능, 실기 통합은 DEV 구현 후 |
| OPS-03 | 역할별 변경을 통합하고 검증 근거를 확인해 GitHub main과 NAS 릴리스를 관리 | 변경 범위·버전·검증 결과·미해결 항목이 식별되는 릴리스 기록 | 인계받은 변경부터 순차 진행 |

- 주로 다룰 영역: `deploy/`, 배포 도구, 운영 설정, `reports/deployment/` 등. 새 경로는 계획이며 필요할 때 생성한다.
- 개발 코드의 의미를 배포 과정에서 임의 변경하지 않는다. 애플리케이션 수정은 DEV에 재현 조건과 함께 돌려준다.
- 기존 공유 폴더의 미완성 `.git`과 잠금을 삭제하지 않는다. Git 취급 방법은 정의서의 Git 상태 주의를 따른다.
- 릴리스 관리를 담당한다는 이유로 실제 자금 투입·실거래 활성화까지 수행하지 않는다.

## 8. 기존 작업·요구사항과 연결

### 8.1 기존 T0~T8의 주담당

| 기존 작업 | 주담당 | 지원·검토 | 연결 업무 |

| T2 KIS 어댑터 | DEV | RES 조건 조사, AUD 검토 | DEV-02, RES-01 |
| T3 영속 저장·주문·대사 | DEV | AUD 검토 | DEV-03 |
| T4 위험 한도·전략 | DEV | RES 실험 가정, AUD 검토 | DEV-04, RES-02 |
| T5 시세·스케줄·상태 | DEV | DES 정보 설계, RES 시장 조건, AUD 검토 | DEV-05, DES-01~03 |

## 9. 착수 순서와 인계

1. **초기 병행 작업:** OPS-01 환경 확인, RES-01 공식 조건 조사, DES-01 운영 흐름, AUD-01 요구 검증표, DOC-01 문서 유지, DEV-01 계약·가짜 증권사 설계를 시작한다.
2. **계약을 맞춘 뒤 구현:** DEV가 공통 모델·설정·주문 상태 계약을 정리하고 DES·RES의 입력을 반영한다. 독립 파일 영역은 나누어 작업한다.
3. **개발·검토 반복:** DEV 자체 테스트 → AUD의 근거 확인 → 발견한 문제를 DEV·DES·RES·OPS 중 해당 소유자가 수정한다. DOC가 변경된 결정을 연결한다.
4. **모의 통합:** 모의 계좌·키가 준비된 기능부터 DEV가 검증한다. 미지원·미검증 항목을 남기고 실제 주문으로 대신 검증하지 않는다.
5. **배포·정리:** OPS가 배포 준비된 버전을 식별해 offline/paper NAS 반영과 복구·공존 상태를 확인한다. AUD가 결과를 평가하고 DOC가 운영·릴리스·인계 기록을 정리한다.
6. **후속 판단:** RES가 비용·성능·자원·실험 결과를 반영해 다음 범위를 제안하고 AUD가 요구 충족·품질 결과를 별도로 갱신한다.

계좌·키가 없어도 오프라인 개발·디자인·조사·검증 계획·문서는 진행할 수 있다. 선행 자료가 필요한 업무만 대기 상태와 필요한 입력을 표시한다. 역할 간 인계는 일상적인 협업이며 매번 사용자 승인을 받는 절차로 추가하지 않는다.

## 10. 파일 소유와 공통 기록

- 새 작업자는 역할 ID와 업무 ID, 담당 파일, 기준 커밋, 예상 산출물을 기록한 뒤 시작한다. 이 문서만으로 특정 Codex가 배정됐다고 표시하지 않는다.
- 각 역할은 자신의 범위에서 수정·검증·커밋할 수 있다. 가능하면 별도 브랜치·checkout을 사용하고 main 통합과 NAS 릴리스는 OPS가 조율한다.
- 공통 모델·DB 스키마·설정 계약은 DEV, 배포·서비스 실행 계약은 OPS, 운영 정보·조작 의미는 DES를 중심으로 관련 역할과 조율한다.
- 요청·정의·분장 문서는 DOC가 일관성을 관리한다. 의미가 바뀌는 수정에는 해당 영역 담당자의 근거를 연결한다.
- 공통 이력 파일을 같은 SMB 작업 경로에서 동시에 덮어쓰지 않는다. 본인 작업 기록을 보존하고 다른 작업자의 기록과 충돌하면 조율해 통합한다.
- 인계 자료에 비밀번호·API 키·토큰·계좌번호·로그 원문을 넣지 않는다. NAS 원본 데이터와 기존 운영 설정의 변경 범위는 요청서의 기준을 따른다.

## 11. 각 Codex에 전달할 첫 지시

| 역할 | 첫 지시 |
